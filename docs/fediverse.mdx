# Fediverse

Mention's ActivityPub implementation is an external-network connector. Native
posts and the Oxy identity graph remain independent of protocol transport, and
the connector registry is the only federation seam used by post workflows.

Local accounts are discoverable as `@username@mention.earth`. Remote actors are
associated with a canonical Oxy federated user ID so feeds and hydration use
the same identity shape for local and remote authors.

## Public protocol surface

These routes are mounted before authentication and before the apex web proxy:

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/.well-known/webfinger` | Resolve an account resource |
| GET | `/.well-known/host-meta` | XRD host metadata |
| GET | `/.well-known/host-meta.json` | JSON host metadata |
| GET | `/.well-known/nodeinfo` | NodeInfo discovery |
| GET | `/nodeinfo/2.0` | NodeInfo document |
| GET | `/ap/users/:username` | Actor document |
| POST | `/ap/users/:username/inbox` | Per-actor inbox |
| POST | `/ap/inbox` | Shared inbox |
| GET | `/ap/users/:username/followers` | Followers collection |
| GET | `/ap/users/:username/following` | Following collection |
| GET | `/ap/users/:username/outbox` | Paginated outbox |
| GET | `/ap/users/:username/collections/featured` | Pinned public posts |
| GET | `/ap/users/:username/posts/:id` | Dereference a post |

ActivityPub endpoint paths must return directly from the backend. Redirecting
an inbox request breaks HTTP signatures and delivery — signatures are
verified against `X-Forwarded-Host`, so the federation routers mount before
`apexFrontendProxy`. The separate browser profile route `/@username` may
redirect a GET with an ActivityPub `Accept` header to the canonical actor
URL; browser requests receive an OG-injected app shell instead.

The actor document's `publicKey.id` host MUST equal the actor `id` host,
`icon.url` must be absolute and reachable, and `/.well-known/host-meta`
must be mounted before auth middleware.

## App-facing federation API

The `/federation` router is distinct from the protocol surface:

| Method | Path | Authentication |
| --- | --- | --- |
| GET | `/federation/resolve` | Optional viewer |
| GET | `/federation/actor/posts` | Optional viewer |
| POST | `/federation/follow` | Required |
| POST | `/federation/unfollow` | Required |
| GET | `/federation/following` | Required |
| GET | `/federation/followers` | Required |
| POST | `/federation/sharing-changed` | Required |

Write handlers enforce identity even though the router supports optional
identity for public reads.

## Consent

Oxy owns `privacySettings.fediverseSharing`; Mention does not persist a second
copy. `packages/backend/src/services/fediverseSharing.ts` is the backend read
path and owns the Mention-side cache. SDK reads bypass the SDK's independent
GET cache so consent decisions use one cache authority.

When sharing is disabled:

- WebFinger and user ActivityPub surfaces return 404.
- New inbound follows and engagement for that local owner are ignored.
- Outbound connector delivery is blocked.
- Undo activities remain allowed so remote and local state can converge.

All federation UI lives under `settings/fediverse/` — add a new row
inside that hub, never beside it. `/transparency` (the bridge-relabelling
and blocklist page) stays a public top-level route, not nested under
settings.

The sharing-change endpoint re-reads the value server-side. Turning sharing off
queues cleanup that broadcasts actor deletion, removes bridged follows, clears
user-scoped federation rows, and invalidates discovery cache. An unavailable
Oxy read is retried by cleanup rather than interpreted as a consent value.

Deleting the Oxy account goes further than turning sharing off: the account
erasure sends a `Delete(Tombstone)` for each public post and a `Delete` of the
actor to every follower inbox, then removes the federation rows. Oxy keeps the
signing key and the event carries the handle, so the Deletes can still be signed
after the account is gone; the delivery worker reads an erased sender's handle
from `account_erasures`. See [Account erasure](./account-erasure.md).

## Inbound flow

```text
inbox request
  -> body and rate limits
  -> HTTP signature verification
  -> actor and target validation
  -> consent check
  -> queue
  -> activity-specific handler
  -> native model / Oxy graph update
```

Follow, Accept, Reject, Undo, Create, Update, Delete, Like, and Announce
activities are dispatched by the shared federation engine and the Mention
content handlers. An inbound follow creates the Oxy graph edge before Mention
sends Accept; the protocol-side follow record is not the app's graph authority.

Remote outbox discovery uses the actor's advertised outbox URL —
guessing `actorUri + '/outbox'` as a fallback breaks PeerTube, Lemmy and
some Pleroma instances, so it is fallback-only. An empty first
author-feed page can schedule a background sync and return `pending: true`, so
the client waits and refetches rather than caching a temporary empty result.
Imported boosts are stored as boost posts and hydrated with their original.

### Remote custom emoji

Mention does not render instance-specific ActivityPub custom-emoji images. At
ingest, the shared Note builder removes only exact shortcodes backed by that
object's `tag.type = "Emoji"` declarations from `content`, every `contentMap`
variant, and `summary`. Undeclared `:text:` and Unicode emoji are preserved.

If nothing remains, the Note is skipped unless real media, an attachment, or a
non-empty content warning remains. The rule is shared by inbox Create, outbox
backfill, boost/quote/ancestor import, and Update. An Update that turns an
existing post into an unrepresentable custom-emoji-only object removes the local
copy through the canonical post-deletion cascade.

## Outbound flow

Eligible local mutations call the connector registry after their native write.
The ActivityPub connector can emit Create, Update, Delete, Like, Undo, and
Announce activities. Delivery is consent-gated and uses server-side
resolution of the author's Oxy identity: fan-out resolves the username
through `resolveFederationUsername` from `oxyUserId`, never from
`req.user.username` — the auth middleware runs without `loadUser`, so
gating on it federates zero posts while everything looks healthy. Callers
pass the post DOCUMENT to `post.create`/`post.update`, never a hand-picked
literal — `LocalPostEventPayload` names fewer fields than the Note builder
reads, so a literal silently drops `sensitive` and quote fields (gate:
`__tests__/connectors/outboundPostPayloadShape.test.ts`). A bare boost must
never federate as an empty `Create(Note)`.

Delivery work is isolated with `Promise.allSettled` and queued when Redis is
available. A connector failure does not roll back a successful native post.
Replies additionally deliver to the parent author's inbox when required.

Collaborative posts are not federated while an invitation is pending. The
publish pipeline fans out only after the last invitation resolves, preventing
an unaccepted collaborator from appearing on the fediverse.

### Remote language declarations

Incoming `language` and `contentMap` values are normalized at ingest, but their
labels are evidence rather than an unconditional distribution grant. Decisive
Japanese kana or Korean hangul corrects a contradictory default; statistical
detection must clear a confidence floor. This prevents a remote account default
such as `en` from placing clearly foreign-language posts in English discovery.
Ambiguous bodies remain unclassified instead of entering For You under a guess.

The reconciled result is stored once in `postClassification.languages`; feeds,
ranking, search, trends, translation selection and outbound ActivityPub consume
that canonical value rather than independently interpreting the remote object.
Semantic changes increment `BASELINE_CLASSIFIER_VERSION` and require the
idempotent post-language backfill for existing rows.

## Discovery and collections

Handle discovery follows:

```text
acct:username@mention.earth
  -> /.well-known/webfinger
  -> actor self link
  -> /ap/users/username
```

The actor advertises its outbox and featured collection. Outbox pages use
keyset pagination, and followers/following collections expose paginated remote
actor URIs. The actor's public-key host matches the actor ID host.

## Remote media

Federated media remains stored as its original remote URL. Browser and native
clients use the backend's guarded media routes:

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/media/proxy?url=...` | Proxy allowed image, video, or audio |
| GET | `/media/poster?url=...` | Produce a bounded video poster |
| GET | `/media/gif?url=...` | Proxy supported GIF media |

Upstream requests use DNS pinning, private-address denial, redirect
revalidation, content-type checks, byte limits, stream abort, and timeouts.
SVG is rejected. Frequently used remote media can be cached in Oxy object
storage when the cache-write feature is enabled.

## Identity and safety on federated surfaces

**Author hydration must NEVER emit a raw `oxyUserId` as a handle.**
Unresolved authors get the degraded summary (empty username, `'Unknown
user'`), never cached.

**OG cards are safety-gated** (`/p/:id`) — a post carrying any sensitivity
signal, or a boost whose original carries one, gets NO `og:image`/body
text; the verdict comes from `requiresContentWarning` and is a REQUIRED
argument to `mapPostOg`.

## Bridged identity, cross-network people, and cross-posts

Three separate questions that are easy to confuse, and are kept apart on purpose.
A fourth section covers an account that moves here, which uses all three.

### 1. Oxy owns external profiles and network identity

Mention passes AP actor URIs, native AT Protocol DIDs and user-entered source
handles to Oxy. Oxy verifies the source, applies its reviewed transport policy,
and returns the canonical public profile, biography, source references and
redirected user ids. Mention does not derive identity from a bridge username,
profile field, display name, avatar or cached actor row.

The cached actor's `uri`, `acct` and `domain` retain transport provenance for
federation delivery and domain moderation. `networkAcct` and `oxyUserId` are
projections of Oxy's response. Profile links use the canonical Oxy handle;
additional source aliases are accepted only when Oxy currently returns them.

A federated account's Oxy record is a mirror minted when Mention first resolved
the actor, so its `createdAt` and follow graph describe the mirror, not the
account. The profile page instead reads the origin's own figures from the
cached actor row: the `followers`/`following` collections' `totalItems` and the
actor's `published` date, which every actor refresh already fetches. `GET
/profile/design/:userId` serves them as `remote` (`services/federation/remoteProfileStats.ts`),
and omits any figure the origin did not report. An ActivityPub actor with no
collection URL, or a row never fetched, has no total. The profile then hides that
stat or the "Joined" line instead of showing `0` or the discovery date. A
collection fetch that fails still stores `0`, because `@oxy.so/federation`
collapses that failure before the row is written.

Mention retains a separate content-only transport list in
`connectors/activitypub/repostTransportPolicy.ts` for rejecting flattened `RT:`
content. That list cannot normalize accounts or establish person equivalence.

### 2. Person equivalence is current, source-bound Oxy evidence

Matching handles across Instagram and Threads do not prove a shared person.
Oxy's verified equivalence requires reciprocal source evidence with immutable
source identity pins and current verification. A recyclable bridge profile URL
alone cannot provide that proof. Unsupported or incomplete evidence keeps the
profiles separate; Mention does not upgrade it with a local attestation.

Oxy preserves original source user ids and exposes the current canonical group.
Mention projects changes by immutable source actor URI, so revocation can restore
one source without transferring another source's posts. Old Mention identity
claim/link tables are audit history only. The manual attestation writer and the
local identity parsers have been retired.

See [source identity reconciliation](./source-identity-reconciliation.md) for the
Oxy-first deployment order, dry-run/apply report, mute preservation and reversal.

### 3. A cross-post is one card and two stored objects

Proving two accounts are one person says nothing about their posts, so
`services/PostEquivalenceService.ts` is a separate concept with its own evidence
hierarchy: a declared original on the object, the same first-party media asset,
one object carrying the other's permalink, and a conservative content fallback.
One more tier, `imported-copy`, pairs a post Oxy Move imported with the
federated copy of the same source post. It is not cross-network, and it is
described under [An account that moves here](#4-an-account-that-moves-here).
Every tier first requires the same currently verified Oxy person, distinct source
networks, compatible text and media, and the appropriate time window. Strong
content resemblance cannot replace identity proof.

Nothing computes a perceptual hash. Both source objects stay stored and
addressable; reader surfaces exclude the non-preferred member with
`notCollapsedCrosspostSql()` **in the query**, so a page of twenty rows is still
twenty cards. The likes tab and bookmarks deliberately do not take that term —
they hand back a collection the reader assembled by hand. Engagement counts are
never summed across networks.

The rendered card names the whole set — `Instagram · Threads` — as a context row
beside "Reposted by" and "Replying to", and the hidden variant's network links
to it at `/p/<id>`. The links are INTERNAL on purpose: both variants are real
Mention posts, and a reader asking for the other version of what they are
already reading should not be sent to a site that may ask them to log in.
Naming the whole set rather than only the hidden half is deliberate too — "also
on Threads" reads as a second, different post, which is the misunderstanding the
collapse exists to prevent.

`scripts/reconcileMetaIdentityAndCrossposts.ts` reconciles data stored before all
of this landed, dry-run by default, delegating every decision to the live
modules.

### 4. An account that moves here

Two things let a Mastodon account move to Mention.

**The alias.** Before a user presses Move, Mastodon requires the target actor's
`alsoKnownAs` to list the old account. Oxy owns the aliases: they are the
user's proven linked accounts marked as aliases. `GET /profiles/username/:username`
returns them, and the federation package puts them in the actor that the actor
route and the `Update(Person)` builder serve.

When an alias is added or removed, Oxy publishes a `profile` event on
`oxy:user:invalidate`. `services/federation/aliasPublication.ts` handles it on
every task:

1. A Redis `NX` claim lets one task handle each event.
2. It skips accounts with no ActivityPub key pair. A federated mirror has
   none.
3. The task reads the profile again and swaps the stored alias set
   (`SET … GET`).
4. Only when the set changed does it raise the existing `actor.update` event.
   That sends the full actor as an `Update(Person)` to the account's followers.

Without Redis, the check does nothing, and remote servers refresh the actor on
their own schedule.

**The Move.** An inbound `Move` is forwarded to Oxy. Oxy verifies it, and then
Mention reattributes the old account's posts here, keeps one card for each
imported post, and unfollows the old account for local users. The steps are in [content import](./import.mdx).

## Optional AT Protocol connector

AT Protocol handle resolution and read/discovery are on unless
`ATPROTO_ENABLED=false`, the same shape as `FEDERATION_ENABLED`. A separate
bridge gate controls repository exposure, and that one is closed by default:
this side reads, the bridge writes. These
features do not change the ActivityPub routes or the native PostgreSQL
authority.

## Instagram: the kilogram bridge and the Graph API

Oxy maps `<u>@instagram.com` to the kilogram.makeup ActivityPub bridge. That
bridge is the preferred road for identity and for new posts, but it never serves
history: its outbox is a bare `{"type":"Collection"}`, and its WebFinger often
answers 429. A kilogram profile therefore opens empty, and it only fills after
someone follows the account and it posts again.

The optional Instagram connector (`packages/backend/src/connectors/instagram/`)
fills that gap. It reads posts from Meta's Graph API through Business Discovery,
and it only reads. It covers every actor whose identity is on instagram.com. For
a kilogram actor that is the `network_acct` domain. It also covers the
`instagram-graph:<ig-user-id>` actors that Oxy returns when no bridge answers.
Those actors are cached with `protocol = 'instagram-graph'`,
`domain = instagram.com` and `acct = networkAcct = <u>@instagram.com`. Their
profile, bio and avatar come from Oxy.

| Variable | Default | Meaning |
| --- | --- | --- |
| `INSTAGRAM_GRAPH_ENABLED` | `false` | Master gate |
| `META_GRAPH_ACCESS_TOKEN` | — | Secret. Long-lived token, sent only in the `Authorization` header |
| `META_IG_BUSINESS_ACCOUNT_ID` | — | The Instagram Business account the token acts as |
| `META_GRAPH_API_VERSION` | `v23.0` | Graph API version |
| `INSTAGRAM_GRAPH_FOLLOW_BACKFILL_LIMIT` | `50` | Posts imported when someone follows |

The connector is inert unless the flag and both credentials are set.

**When posts are read.** Each sync takes a per-actor lease
(`federated_actors.instagram_graph_*`), so concurrent triggers make one set of
calls. Profile-view and follow syncs run on the `instagram-graph-sync` queue
worker; they run detached in the API process only when there is no queue. A run
stops starting new work after 20 minutes, which keeps it inside its 30-minute
lease, so a reclaimed lease never repeats downloads.

- A profile view imports one page, at most every 6 hours per actor. The profile
  reports `pending` only until a first sync has finished, so it does not flicker
  between a spinner and an empty page.
- A follow imports up to `INSTAGRAM_GRAPH_FOLLOW_BACKFILL_LIMIT` posts, at most
  every 2 hours per actor. A follow/unfollow loop, or many followers, therefore
  costs one backfill. The depth walked is recorded
  (`instagram_graph_history_depth`), so the backfill walks history once, until
  it reaches that depth or the listing ends. A profile view's single page does
  not count toward it.
- The `syncInstagramFollowedAccounts` periodic job runs every 30 minutes. It
  syncs up to 10 actors that have an accepted local follower, 2 at a time.

The periodic job and profile views after a successful sync stop paging at the
first page that holds an already-imported post; a key that is only claimed does
not count as imported. A run cut short by its deadline resumes after 15 minutes
instead of the full cooldown.

**Budget.** A token gets about 200 calls per hour. Every call must first take a
token from a bucket in Redis (a per-process bucket when Redis is unavailable).
The bucket refills at 150 per hour with a burst of 30, and background calls
cannot draw it below 15. Taking a token is one Lua script, so concurrent tasks
cannot overspend. The `x-app-usage` header is also recorded and decays over one
hour: background calls stop at 75% usage, and profile views and follows stop at
95%. Throttle strikes use an atomic `INCR`.

| Error code | Meaning | Response |
| --- | --- | --- |
| 4, 17, 32, 613 | Throttled | Back off exponentially, from 15 minutes up to 2 hours |
| 190 | Invalid token | Pause for an hour and log once at `error`. Neither the token nor a URL is ever logged. |
| 110 / 2207013 | Not a Business or Creator account | Remember it and re-ask weekly. Personal accounts cannot be read. |

**Identity pin.** The first successful sync stores the Instagram user id that the
username answered with (`instagram_graph_user_id`). If a later answer carries a
different id, the username has been recycled: the sync imports and deletes
nothing, records `identity_mismatch`, and waits a week before asking again.

**What is imported.** Each post goes through `getPostCreator().create` with
notifications, socket emits and federation delivery skipped, and it keeps its
original `createdAt`. The caption becomes the text; bare `@handles` are qualified
onto instagram.com and hashtags are extracted. Media is re-hosted in Oxy at
import. Meta's CDN URLs expire (`oe=`), so an Instagram post never keeps one:

- A carousel imports every child, in order.
- A video that Instagram serves only as a thumbnail (licensed audio) imports that
  thumbnail as an image.
- A video that cannot be stored, for any reason, falls back to its poster image.
- A file that will never be storable (404/410, over the size cap, not media) is
  dropped.
- A failure that may pass (media writes off, Oxy unavailable) leaves the whole
  post for the next sync rather than storing an expiring link.

**One post, two roads.** A Graph-imported post is stored with
`federation_activity_id = instagram:<shortcode>`, with the shortcode taken from
the permalink. A kilogram Note's id is
`https://kilogram.makeup/users/<u>/statuses/<shortcode>`, measured live. Both
roads write `instagram:<shortcode>` into `post_source_keys` under a UNIQUE key,
in the same transaction as the post, so whichever road arrives second collides
instead of duplicating.

- The Graph import **claims** the key before it downloads anything, and the post
  insert fills the claim. A kilogram push racing it collides, and its inbox job
  retries into the finished post, so no upload is made for a post that then
  loses. oxy-api has no route to delete a durable federation asset.
- Every "is this object already here?" gate on the ActivityPub side matches on
  the key. It uses an uncorrelated lookup, so it stays index-driven;
  `instagramSourceKeyPlan.test.ts` asserts that the plan never scans `posts`. A kilogram Like, boost, reply, Delete or Update of a Graph-imported
  post reaches the existing row. Ownership is still checked against the signing
  actor.
- Graph posts of a kilogram actor are stored under the kilogram actor URI, so
  identity projection, cross-post detection and a bridge Delete treat both roads
  as one source.
- **Posts deleted on Instagram are removed, on the second observation.** The
  media listing is newest-first and contiguous, so a stored post that the
  listing no longer has probably was deleted. The window runs after the oldest
  listed entry (exclusive bound) up to the newest.
  - The first observation only marks the post (`post_source_keys.missing_since`).
    A later sync that still does not list it removes it.
  - Listing the post again clears the mark.
  - Every listed item counts as present, including one with nothing importable.
  - More than 10 missing posts from one listing is treated as an anomaly, and
    nothing is marked or removed.

**Deleting re-hosted media.** When a federated post is deleted (a bridge
`Delete`, a post gone from Instagram, or any other deletion), its re-hosted Oxy
files are deleted too, including the poster frame of a video.
`federated_media_posters` records those poster frames.

- The files are queued in `federated_media_deletions`, in the same transaction
  that deletes the posts.
- A periodic drain (`drainFederatedMediaDeletions`, every minute, at most 5 calls of 20 files, not gated on
  any flag) calls oxy-api's `POST /assets/service/federation/delete`.

Oxy stores one file per content hash, so a file id can be shared by another
post, a variant or a federated banner. The drain therefore re-checks every
reference before deleting anything. It does this under a per-file advisory lock
that the post insert also takes, so an import reusing the id either commits
first (the file is kept, `in_use`) or finds a tombstone and retries later with a
fresh upload.

Only an answer from Oxy settles a deletion:

- `deleted` and `not_found` are done. The tombstone is kept, because file ids
  are never reused.
- `forbidden` is logged and dropped.
- `in_use` means Oxy keeps the file because another owner or app also holds it.
  It is settled and logged, with no retry. A result this build does not know is
  retried later.
- **Reuse:** Oxy dedupes uploads by content hash and reactivates a trashed file
  under its old id. An upload that started after Oxy confirmed the delete
  (`settled_at`) re-opens the id. Any earlier or overlapping upload is refused
  by the post insert, and the import retries.
- **Owned elsewhere:** a 409 `FEDERATED_MEDIA_OWNED_ELSEWHERE` on upload is
  permanent for that item. Instagram falls back to the poster, or drops the
  item, and never stores the expiring URL. ActivityPub and atproto keep the
  stable URL behind the media proxy.
- A 429 (honouring `Retry-After`), a 5xx, a transport failure, or a 404 for the
  route itself (an oxy-api that predates it) is retried with exponential backoff.

Nothing is sent to Instagram. Replies, likes and boosts of a Graph-imported post
are not delivered, and the permalink stands in as the object a reply or quote
references.

**Migration 0054 and its post-deploy step.** `post_source_keys` is a new child
table rather than a `posts` column. A column plus unique index on `posts` would
hold ACCESS EXCLUSIVE on `posts` for the whole index build inside the
transactional migrator.

- Measured with `pg_locks`, the migration takes only SHARE ROW EXCLUSIVE on
  `posts`, so reads continue.
- It adds the widened CHECKs on `federated_actors` and `federated_follows` as
  `NOT VALID`, so it scans no rows under their ACCESS EXCLUSIVE.
- After the deploy, run `packages/backend/src/scripts/backfillInstagramSourceKeys.ts` (`DRY_RUN`
  first). It gives pre-0054 kilogram posts their source key, batched per bridge
  actor through the actor-URI index, then runs `VALIDATE CONSTRAINT` on the three
  CHECKs. VALIDATE does not block reads or writes. Until the script runs, the
  Graph import still recognises those posts by their bridge Note id.

**Protocol types.** `instagram-graph` is a first-class protocol upstream:
`@oxy.so/contracts` 4.0.0 accepts it in the external-identity schemas and
`@oxy.so/federation` 2.2.0 includes it in `NetworkId`.

## The connector contract

Mention's content core (`PostCreationService`, the feed engine, notifications)
never imports ActivityPub or AT Protocol code directly. It talks to
`ConnectorRegistry`, which fans a `LocalNetworkEvent` out to every enabled
`NetworkConnector`. Both the contract and the normalized DTOs it trades in
(`NormalizedExternalActor`, `NormalizedExternalPost`, the `LocalNetworkEvent`
union) ship from the shared `@oxy.so/federation` package — not a Mention-local
type — so `ActivityPubConnector` and `AtprotoConnector` are two
implementations of one interface Mention does not own:

```ts
interface NetworkConnector<TContent = unknown> {
  readonly id: NetworkId;
  readonly enabled: boolean;
  matches(subject: string): boolean;
  resolve(handle: string): Promise<NormalizedExternalActor | null>;
  fetchProfile(externalId: string): Promise<NormalizedExternalActor | null>;
  fetchPosts(externalId: string, opts?: FetchPostsOptions): Promise<FetchPostsResult>;
  deliver(event: LocalNetworkEvent<TContent>): Promise<void>;
  receive(payload: unknown, ctx: ReceiveContext): Promise<void>;
  mapIdentity(actor: NormalizedExternalActor): Promise<string | null>;
}
```

**What capability discovery looks like today.** There is no `getCapabilities()`
method — instead, `AtprotoConnector.deliver()` switches on every
`LocalNetworkEvent` kind and no-ops the write-side ones with an in-source
comment explaining why ("Mention does not publish posts, reposts, edits,
deletes, likes, or actor changes into a foreign atproto PDS"). That is a
documented, deliberate design choice, not an unimplemented method throwing —
`ConnectorRegistry.deliver` fans out via `Promise.allSettled`, so a connector
that has nothing to do for an event kind returning cleanly is the intended
shape.

**The real gap** is that this is legible to a person reading the source, not
to a caller asking the interface a question before it acts — there is no
machine-checkable "can connector X publish/delete/follow" a caller could use
to skip the call, or a contract-test suite every implementation of
`NetworkConnector` must pass for the operations it actually performs. Adding
either is a change to `@oxy.so/federation` itself, which Mention does not own
(`@oxy.so/services`/`@oxy.so/core`'s home repository does) — per this repo's
"fix upstream, never patch" rule, that is upstream work, tracked as
[OxyHQ/oxy#971](https://github.com/OxyHQ/oxy/issues/971), not a local
reimplementation of the interface.

Adding a third protocol to Mention means writing one more `NetworkConnector`
implementation under `connectors/<protocol>/` and registering it in
`ConnectorRegistry` — no changes to `PostCreationService`, the feed engine, or
any other product code, because none of it references a protocol by name.

## Deployment routing

Both `mention.earth` and `api.mention.earth` reach the Mention backend on AWS
ECS. The apex is Cloudflare-proxied to the same load balancer; the API host is
DNS-only. The backend mounts `/.well-known`, `/ap`, protocol bridge routes, and
`/media` before web-shell and static-proxy handling. Do not reintroduce a
Cloudflare Worker or Pages Functions in front of the apex — it is served
entirely by the Mention backend.

No application worker sits in front of the apex. Signed inbox requests must
reach the backend without a zone-level redirect.
