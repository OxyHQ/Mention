# Architecture

Mention is a Bun monorepo whose runtime boundaries match its four workspaces.
Shared contracts can change atomically, but each runtime has a separate entry
point and production artifact.

## Workspace boundaries

```text
packages/shared-types ───────────────┐
        │                            │
        ├──> packages/backend <──────┼── packages/mcp
        │           │                │
        └──> packages/frontend ──────┘
```

| Workspace | Boundary |
| --- | --- |
| `frontend` | Presentation, navigation, viewer-scoped cache, local persistence |
| `backend` | Domain commands and queries, HTTP, sockets, workers, integrations |
| `shared-types` | Portable contracts; no runtime application state |
| `mcp` | MCP protocol, OAuth resource validation, sessions, and backend calls |

`bun run build` builds shared types before the backend and MCP. The web export
is separate because it produces a static Expo artifact.

## Frontend

The Expo 56 app targets native and web from Expo Router routes. TanStack Query
owns remote server state, while Zustand stores local UI state. Viewer-private
query keys include the viewer identity; account transitions cancel in-flight
work, remove the previous private cache, clear persisted identity state, and
disconnect the previous socket.

Long feeds use virtualized lists and bounded pagination. Native and web database
implementations are split so the browser does not import the native SQLite
runtime. Audio, video, composition-heavy code, and non-initial routes are
loaded at their feature boundary rather than the root provider.

The web build emits browser telemetry through `/telemetry/web`. The payload is
bounded and contains normalized routes, Core Web Vitals, navigation events, and
runtime/load failures.

## Backend composition

The backend is assembled from explicit runtime services rather than importing
state from the server entry point:

```text
configuration
    │
    ├──> Mongo supervisor and schema state
    ├──> Redis state, cache, queues, locks, and pub/sub
    ├──> Express application and route dependencies
    ├──> Socket.IO and distributed presence
    └──> schedulers, workers, connectors, and MTN services
```

Configuration is parsed with Zod during startup. Feature-specific variables
become required only when that feature is enabled. Request handling uses one
central Mongo connection; handlers do not reconnect per request.

Public and authenticated routers are separate. Authentication accepts an Oxy
access token or an eligible MCP JWT. Public reads may use optional identity for
viewer state, while mutations enforce identity.

`PostHydrationService` is the only authority for post response DTOs. It performs
bulk user resolution, bounded fallback work, and viewer-aware hydration without
letting controllers build competing post shapes.

## Feed engine

The MTN feed engine is under `packages/backend/src/mtn/feed`. A validated
descriptor selects a registered source and preset. The engine then applies
viewer context, filters, ranking signals, pagination, and hydration.

Supported descriptor families include:

- `following`, `for_you`, `explore`, `videos`, `media`, `saved`, and `trending`
- `mutuals`, `friends_popular`, and `friends_of_friends`
- `author|<oxyUserId>|<tab>`
- `hashtag|...`, `topic|...`, `list|...`, `custom|...`, and `feedgen|...`

The request-scoped viewer context resolves graph membership, language settings,
blocks, restrictions, and Mention mutes once. Excluded authors are removed
before pagination. Chronological cursors use `(createdAt, _id)` where that is
the feed's declared sort axis.

## MTN signed records

The signed-record layer lives under `packages/backend/src/services/mtn`:

- `MentionRecordService` signs and appends eligible local records.
- `MentionRecordStore` persists the chain and repository head.
- `PostMaterializer` projects verified records into the application post model
  idempotently.
- Node registry, sync, and scheduling support user-operated Mention nodes.

MongoDB remains authoritative for application reads. Record append is
best-effort and isolated from the native write result. Protocol verification
uses Oxy verification methods for self-issued records and configured Mention
keys for custodial records.

## External networks

External behavior is behind `packages/backend/src/connectors`. The registry
contains only enabled connectors and fans out with `Promise.allSettled`, so one
network cannot abort another or the native post write.

- ActivityPub is enabled unless `FEDERATION_ENABLED=false`.
- AT Protocol discovery/read support is optional through `ATPROTO_ENABLED`.
- The AT Protocol bridge remains independently gated by
  `ATPROTO_BRIDGE_ENABLED`.

Post creation depends on the registry's narrow federation interface, not a
network implementation. Protocol DTOs at the connector boundary do not depend
on Mongoose.

## Storage and degradation

| Dependency | Use | Failure behavior |
| --- | --- | --- |
| MongoDB | Authoritative application data and schema version | Readiness fails |
| Valkey/Redis | Cache, queues, rate limits, locks, Socket.IO adapter, presence | HTTP degrades quickly |
| Oxy | Identity, settings, graph, service-backed media | Endpoint-specific degraded behavior |
| Object storage | Canonical and cached media | Media operation fails or falls back |

Redis health is tracked locally with a shared connection attempt and circuit
breaking. Normal operations do not issue a `PING`. A process never assumes
singleton leadership when it cannot acquire the distributed lock.

## Process lifecycle

Startup runs in this order:

1. Validate configuration.
2. Connect MongoDB with bounded retry.
3. Run migrations outside production, or verify the deployed schema in
   production.
4. Initialize Redis-backed optional capabilities.
5. Register sockets, workers, outbox processing, and leader-gated jobs.
6. Start HTTP and mark readiness true.

Shutdown first marks readiness false and stops accepting HTTP. It then stops
schedulers and workers and closes Socket.IO, pub/sub, Redis, and MongoDB in
parallel. A hard ten-second deadline prevents a stuck deployment drain.

## Local topology

`docker-compose.yml` reproduces the transactional data requirements:

```text
mongo ──healthy──> mongo-init ──completed──┐
valkey ─────────────healthy────────────────┼──> migrate ──completed──> backend
```

MongoDB runs as a single-node replica set so transactions behave like
production. The migration container and backend use the same locally built
backend image. MongoDB and Valkey expose loopback-only ports and persist to
named volumes.

## Production topology

```text
                     ┌── api.mention.earth ──┐
Internet ── ALB/CF ──┤                       ├── ECS mention :3000
                     └── mention.earth ──────┘        │
                                                      └── static web origin

MCP client ── ALB ── mcp.mention.earth ── ECS mention-mcp :3100
```

The backend handles federation and OG routes before proxying remaining apex
GET/HEAD requests to the static Expo origin. Hashed assets receive immutable
caching; HTML revalidates. A hashed asset URL that resolves to HTML is rejected
as a non-cacheable 404.

Deploy workflows run only after successful CI on `main`. Images are addressed
by commit SHA/digest. Production migrations run once before rollout, and the
same artifact is used for migrations and the service.
