# API

The Mention backend is an Express 5 application served primarily from
`https://api.mention.earth`. The apex host reaches the same process for
ActivityPub, OG shells, and static web proxying.

This page describes route families and stable operational contracts. Individual
controllers remain authoritative for endpoint-specific request bodies and
response shapes.

## Authentication

Authenticated API routers accept an Oxy bearer token or a valid Mention MCP
JWT. Public read routers may attach optional viewer identity to calculate
visibility and viewer state. Mutations require identity in their mount or
handler.

Post responses are hydrated by `PostHydrationService` and use contracts from
`@mention/shared-types`. Oxy's user object is the canonical post-author shape.

## Operations

| Method | Path | Access | Contract |
| --- | --- | --- | --- |
| GET | `/health/live` | Public | `200` while the process can answer HTTP |
| GET | `/health/ready` | Public | `200` only after startup, migrations, and PostgreSQL; otherwise `503` |
| POST | `/telemetry/web` | Trusted browser origin | Bounded web-vitals/runtime batch; returns `204` |

A ready response reports the runtime phase and PostgreSQL, migration, and Redis
states. Redis can be `degraded` without failing HTTP readiness.

Metrics use normalized route templates and bounded labels. The service does not
expose user IDs, post IDs, raw paths, query values, tokens, or private content
as metric labels.

`POST /posts/:id/translate` is the only published-post path that calls
inference. It caches the result on the post as a `source: 'machine'` variant
under the canonical exact BCP-47 tag (`es-MX` and `es-ES` are separate
entries; a base-only `es` stays `es`), and hydration serves that cached
rendition to later readers of the same locale without calling the model.
Concurrent requests for the same post and tag share one translation. Within a
backend task this uses an in-flight map, and across tasks it uses a short-lived
Redis lock (`mention:translation:<postId>:<tag>`). A task that finds the lock
held waits, then serves the variant the holder stored. If Redis is unavailable,
each task translates on its own, and the database still keeps one row per tag.
If the author edits the post while it is being translated, the stale result is
dropped and the new source is translated once. A second edit during that retry
returns `409 { code: 'TRANSLATION_SOURCE_CHANGED' }`, and nothing is cached.

Model output is checked before it is stored or returned, for both endpoints
(`packages/backend/src/services/translationOutputGuard.ts`). Before the text is sent, every entity
the post renderer links (`scanTextEntities`: `[mention:<id>]` placeholders,
`[@Label](target)` mentions, `@handle` and `@user@domain`, `#hashtags`,
`$CASHTAGS`, URLs) is replaced with an opaque `⟦n⟧` token. The answer has one
echoed `<text>` wrapper or code fence removed, and then it must contain every
token exactly once and unchanged. If it does not, or if it is empty, the request
returns `502 { code: 'TRANSLATION_OUTPUT_INVALID' }` and nothing is cached. When
an ALT or article field fails the same check, that field is left out of the
stored variant. The stored translation keeps `[mention:<id>]` placeholders; the
response's `translatedText` renders them as hydration does (`[@Label](handle)`).
A Kaana rate limit answers `429`, a billing limit `502`, and any other inference
failure `503` (`classifyKaanaFailure` in `utils/kaana.ts`).

`PUT /posts/:id` drops every machine variant, along with its localized ALT
rows, when an edit changes what the variants were translated from: the primary
body, the ALT text of the media it shows, or the article.

Collaboration invite actions and threadgate/postgate operations also live under
`/posts/:id`. Consult the exported shared types and route validators before
changing their payloads.

## Search and statistics

### `GET /search/overview`

One request for the search screen's whole overview, replacing four of the seven
the client used to fire. Mounted on the PUBLIC api with `optionalAuth`, one
mount before the authenticated `/search`: this router declares only
`/overview`, so `GET /search` falls straight through to the authenticated one
(the same two-mounts-one-prefix arrangement `/posts`, `/statistics` and
`/channels` use). Being public is deliberate — a signed-out viewer gets real
results instead of a 401.

The response contract is `SearchOverviewResponse` in
`@mention/shared-types/search`. Two things about it are load-bearing:

**Every lane key is always present, with an explicit `status`** — `ok`,
`timeout`, `error`, `skipped` or `unavailable`. An absent key and an empty array
are indistinguishable on the wire, so a client that only received arrays could
not tell "nothing matched" from "this lane fell over", and rendered a confident
"no results" for an outage. `timeout` and `error` are separate because a
timeout is worth retrying and an error usually is not.

**`skipped` is not degraded; `unavailable` is.** `skipped` means the lane was
deliberately not run for this request (`profiles` is Oxy's own endpoint).
`unavailable` means the client still has to fetch it separately — `posts` and
`saved` today, because both need post hydration with the viewer's privacy
context. The `degraded` flag counts the second and not the first, or it would
be true on every search and carry no information.

Lanes run concurrently under two bounds: a Postgres `statement_timeout`, which
is what actually stops the query, and a wall-clock race for the parts that are
not Postgres. `utils/withStatementTimeout.ts` records why a race alone bounds
nothing that matters — the promise is abandoned while Postgres keeps executing
and keeps its pooled connection.

The viewer-independent lanes (hashtags, public feeds, starter packs) share one
stale-while-revalidate cache entry. `lists` is computed per request because it
mixes public rows with the viewer's own, and a shared entry would show one
viewer another's private list.

### `GET /search`

Searches only published, visible posts. It uses PostgreSQL full-text search — a
generated `tsvector` column queried with `websearch_to_tsquery('english', …)` —
a minimal projection, a bounded execution time, and an opaque, versioned cursor
over `(createdAt, id)`.

## MCP OAuth and account binding

New MCP connections authorize through Oxy's central authorization server at
`api.oxy.so`. Consent selects exactly one account, and Mention validates every
central token through live, service-authenticated introspection before applying
the catalog capability required by the exact API route.

Mention-owned OAuth routes remain mounted only as a retirement surface:

| Method | Path | Access |
| --- | --- | --- |
| GET | `/.well-known/oauth-authorization-server` | `410 Gone`; points clients to Oxy |
| GET | `/.well-known/oauth-protected-resource` | `410 Gone`; resource metadata is served by `mcp.mention.earth` |
| POST | `/mcp/oauth/register` | `410 Gone` |
| GET | `/mcp/oauth/authorize` | `410 Gone` |
| POST | `/mcp/oauth/approve` | `410 Gone` |
| POST | `/mcp/oauth/token` authorization-code grant | `410 Gone` |
| POST | `/mcp/oauth/token` legacy refresh grant | Existing legacy families only, until `2026-10-02T00:00:00Z` |
| GET | `/mcp/bundles/link/preview` | `410 Gone` |

For central tokens, the account routes read Oxy's connection, not a Mention
table: `/mcp/bundles/accounts` lists every account the connection may act as,
`/mcp/bundles/me` names the one it is acting as, `POST /mcp/bundles/link-token`
returns a single-use `auth.oxy.so` link that adds another account (approved
there, as that account), and `POST /mcp/bundles/active` asks Oxy to act as a
member — Oxy refuses one that never approved this connection. Legacy bundles keep
their existing members until the fixed cutoff but cannot be widened: their link
endpoints stay `410 Gone`.

The MCP resource and JWT audience are exactly `https://mcp.mention.earth`
without a trailing slash. Unauthenticated MCP requests receive a bearer
challenge.

## Request behavior

- JSON request bodies are limited to 1 MiB, including ActivityPub JSON types.
- Pagination and error bodies are endpoint-specific; do not assume one global
  envelope.
- Feed and search cursors are opaque and must be returned unchanged.
- API rate limiting excludes the apex browser asset plane.
- Structured request logs include a request ID, normalized route template,
  duration, and result without secrets or private payloads.

## Private Deck workspace

`GET /deck` and `PUT /deck` require the current account's authenticated session.
The session supplies ownership; no target account id is accepted. Both responses
use `Cache-Control: private, no-store` and the raw `{ revision, state }` contract
from `@mention/shared-types/deck`. An account with no workspace receives
`{ revision: 0, state: null }`; the frontend supplies its current defaults.

A PUT sends `{ baseRevision, state }`. Initial insertion and later updates are
atomic compare-and-swap operations. Exactly one competing writer succeeds; a
stale revision receives HTTP 409 with the latest `{ revision, state }`, allowing
the client to reconcile its pending edits without silently replacing another
device's workspace. Revisioned state includes ordered panels, their settings,
independent navigation histories, selected entries, and Bloom scroll snapshots.
Only references and UI configuration are stored, never fetched feed/profile data.
The optional boolean `homeScreen` opens Deck as desktop Home; omission defaults to
false. It follows workspace synchronization, so disabling sync preserves the
server’s previous home preference along with its panels.

Setting `syncEnabled: false` persists the preference while preserving the server's
previous workspace. If none exists, the stored disabled workspace has empty
panels/order. Disabled clients retain their local edits; enabling sync again sends
the local snapshot with the current revision. Unauthenticated use stays local.
The API rejects unknown fields, external navigation URLs, malformed Unicode,
invalid dimensions/history/selection, over 24 panels, over 100 history entries or
256 scroll offsets per panel, and bodies over 512 KiB. Account erasure removes the
complete private document. The channel-content deletion cascade also removes a
workspace owned by that channel account; other accounts' workspaces remain intact
even when their history references the channel. Migration `0079_deck_workspaces`
is additive and runs before deploying the image that serves these endpoints.
