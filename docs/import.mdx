# Content import

Oxy Move is a separate first-party app. It reads a user's old Mastodon,
Bluesky or other account and brings that content into Mention. Mention does
not read other platforms itself. It exposes one server-to-server ingest API,
and each imported item becomes an ordinary native post of the user.

| Piece | Where |
| --- | --- |
| Routes and validation | `packages/backend/src/routes/imports.ts` |
| Import logic | `packages/backend/src/services/PostImportService.ts` |
| Import ledger (`post_imports`) | `packages/backend/src/db/schema/imports.ts` |
| Platform list and labels | `IMPORT_PLATFORMS`, `IMPORT_PLATFORM_LABELS` in `packages/shared-types/src/post.ts` |

## Who may call it

Only Oxy Move's verified workload may import for the original account. Use
`mentionForOxyService` from `@oxy.so/mention-sdk/server`; it uses the shared Oxy
transport, canonical receiver audience and the shared import contracts. The
caller application must equal `MOVE_APPLICATION_ID`.

The caller supplies the original verified session or its own durable Oxy task
through the SDK requester option. Oxy validates the requester and effective
account on every call. A user ID header, the application's brand, an API key or
an old `internal` tier does not authorize an import. Own calls have no OAuth
scopes or per-app consent.

Every other caller gets `403`: user sessions sent directly to these service
routes, MCP connections, capability tickets, other own services, external
credentials and Move without valid original requester authority. If
`MOVE_APPLICATION_ID` is unset, nobody can import. Managed Mention deployments
must also set their registered `MENTION_SERVICE_APPLICATION_ID`; callers set
`receiverApplicationId` to that same registration.

Two error codes:

- `IMPORT_CALLER_NOT_ALLOWED`: the caller is not the verified own Move workload.
- `IMPORT_USER_REQUIRED`: the original requester did not authorize this account.

Import IDs, batching, repeated lookup parameters, ledger uniqueness and undo
semantics remain the domain contract below. A response lost after a mutation
has an unknown outcome: retain the original batch and reconcile through lookup.
See [the migration ledger](./first-party-platform.md) for source versus rollout
status and the pending Move/Schedio caller cutover.

The routes use the backend's normal per-user rate limits, keyed on the
delegated user. The JSON body limit is 1 MB per request.

## `POST /imports/v1/posts:batch`

Imports up to **50** items, in the order sent.

```json
{
  "platform": "mastodon",
  "batchId": "<Move job id>",
  "items": [
    {
      "sourceId": "109876543210",
      "sourceUrl": "https://mastodon.social/@alice/109876543210",
      "sourceAccountId": "https://mastodon.social/users/alice",
      "sourceItemId": "109876543210",
      "createdAt": "2019-03-04T05:06:07.123Z",
      "text": "Plain text body",
      "contentWarning": "spoilers",
      "language": "en",
      "visibility": "public",
      "replyToSourceId": "109876543200",
      "quoteSourceId": "109876543100",
      "media": [{ "assetId": "<Oxy asset id>", "alt": "a cat" }],
      "article": { "title": "Title", "body": "Long-form body" },
      "links": ["https://example.com/linked"]
    }
  ]
}
```

- `platform` is one of `mastodon`, `bluesky`, `threads`, `instagram`, `x`,
  `facebook`, `medium`, `substack` or `telegram`.
- `batchId` is the unit that undo deletes. Use Move's job id.
- `sourceId` is the item's **dedupe key**: unique among everything its platform
  can produce. Where the platform's own item id is only unique within one
  account (a Telegram message id restarts in every channel), send
  `<sourceAccountId>/<sourceItemId>`.
- `sourceAccountId` and `sourceItemId` (optional) record where the item came
  from in structured form, as the platform names it:

  | Platform | `sourceAccountId` | `sourceItemId` |
  | --- | --- | --- |
  | Telegram | channel id (no `-100` prefix) | message id |
  | Mastodon | actor URI | status id |
  | Bluesky | DID | record key |

  They are stored in `post_imports.source_account_id` / `source_item_id` and are
  provenance only, never part of the dedupe key.
- `createdAt` is ISO 8601 with an offset. It is stored to the millisecond, and
  anything finer is dropped. A date more than one hour in the future is refused.
- `text` is plain text, up to 25,000 characters with the appended links.
  - An `@handle` in it stays text. No mention is created and nobody is notified.
  - A `#hashtag` becomes a hashtag, as in a normal post.
- `visibility` is `public` or `followers_only`.
- `media` holds up to 10 Oxy asset ids that Move has already uploaded as the
  user's media.
  - Each asset must exist, be `active`, and belong to the acting user; Oxy
    reports the owner to internal apps only, so an owner it does not report is
    refused as `media_not_owned` too.
  - Its MIME type sets the kind: an image, a GIF (`image/gif`) or a video.
- `links` holds up to 10 URLs that the source showed outside the text, such as
  Bluesky link facets. Any link not already in `text` is added to the end of
  the body.
- `article` sets a long-form body, stored like a composer article.
- `replyToSourceId` and `quoteSourceId` name items **this same user imported
  from this same platform**, either earlier in the batch or in an earlier
  batch. For a reply to someone else's post, leave out `replyToSourceId`.
- A reply to one of the user's own posts joins that post's thread.

The response is `200`, with one result per item in input order:

```json
{ "results": [{ "sourceId": "109876543210", "status": "created", "postId": "..." }] }
```

| `status` | Meaning | Written? |
| --- | --- | --- |
| `created` | A new post exists; `postId` is its id | yes |
| `existing` | This user already imported this `(platform, sourceId)`; `postId` is that post | no |
| `deferred` | `error` is `parent_not_imported` or `quote_not_imported`. Send the referenced item first, then resend this one, or resend it without the reference to import it standalone | no |
| `failed` | `error` gives the reason: `empty`, `created_at_in_future`, `text_too_long`, `media_not_found`, `media_not_owned`, `media_unsupported`, `media_lookup_failed` or `internal_error` | no |

If the body itself is malformed, the whole request gets `400` with
`INVALID_IMPORT_BATCH`, and nothing is written.

## `DELETE /imports/v1/batches/:batchId`

Undoes one batch, deleting only the **acting user's** posts from that batch. It
answers `{ "deleted": n, "failed": m }`.

Every post is deleted through the normal delete path
(`PostDeletionService.deleteAuthoredPost`), newest first:

- Replies go before their parents, so each post gets its own federated
  `Delete`.
- Each public post sends a `Delete(Tombstone)` and an MTN tombstone.
- Replies from other users are deleted with their parent, as with any post
  deletion.

A post the author already deleted counts in neither number.

## `GET /imports/v1/lookup`

Query: `platform=`, `sourceIds=` and `federatedIds=`, each repeated once per id
(`?sourceIds=a&sourceIds=b`). Each list takes up to 200 ids. Values are never
split on commas, because an id is often a URL and a URL may contain one.

```json
{
  "imported": { "<sourceId>": "<postId>" },
  "federated": {
    "<AS2 id or at-uri>": { "postId": "...", "actorUri": "...", "url": "...", "oxyUserId": "..." }
  }
}
```

- `imported` covers only this user's own imports.
- `federated` lists the public, published federated posts Mention already stored under
  that ActivityPub object id or at-uri (`posts.federation_activity_id`). These
  are copies of the old account's posts that federation brought in before the
  user moved.

This endpoint only reports what exists. The copies become the user's own
posts ("adoption") when the old account sends a verified ActivityPub `Move`
(see below). After that, `oxyUserId` on a copy is the user.

## Adoption on `Move`, and one post instead of two

A user moving from Mastodon links the old account in Oxy, imports with Move,
and then presses **Move** on the old account. Mastodon sends a `Move` to every
server that follows it. Mention's inbox handles it in
`connectors/activitypub/move.service.ts`:

1. **Shape check.** The federation engine (`parseInboundMove` in
   `@oxy.so/federation`) requires `actor` and `object` to be the verified HTTP
   signer, and `target` an `https` URI that is not the actor. A Move that
   fails is dropped before Oxy is called.
2. **Oxy decides.** Mention calls `POST /federation/move` with
   `{ oldActorUri, targetActorUri, activityId }` using its service credential.
   Oxy checks the alias and a fresh `movedTo`, moves the follows and redirects
   the old account to the target.
   - A `4xx` from Oxy (such as `alias_missing` or `moved_to_mismatch`) is a
     refusal. Mention logs `[Federation] Move refused by Oxy` with the `code`
     and drops the activity.
   - A `5xx` (such as `502 old_actor_unreachable`), a `408`, a `429` or a
     network failure throws, and the inbox job retries.
   - Oxy is idempotent on `activityId`. The same Move arriving at several
     inboxes, or a retry, replays the first result.
3. **Reattribution.** The old actor's posts here become the target user's,
   through the same source-identity projection the resolver uses
   (`reconcileActorIdentityProjection`, see
   [source identity reconciliation](./source-identity-reconciliation.md)).
   Post ids, replies, likes and moderation stay on the same rows.
4. **One post, not two.** An imported post and the federated copy of the same
   source post are now both the user's. `collapseImportedCopies`
   (`services/PostEquivalenceService.ts`) puts each pair into a cross-post
   cluster with `imported-copy` evidence:
   - The pair matches when the ledger's `sourceId` or `sourceUrl` equals the
     copy's AS2 id or its `url`, and both posts have the same owner.
   - The **federated copy is shown**, and the import is collapsed. Remote
     replies, likes and boosts address the copy's AS2 id, so the conversation
     is on the copy.
   - **Nothing is deleted.** Both posts keep their ids, replies and likes, and
     the collapsed import stays reachable at `/p/<id>`. Feeds, profiles and
     search show one card (`notCollapsedCrosspostSql`). The card shows no
     network label, because both posts are from one network.
   - **It is reversible.** If Oxy withdraws the Move and the old actor is
     projected back, the two posts have different owners again. The projection
     dissolves the cluster, and both posts are visible again.
   - **Order does not matter.** The Move collapses imports that already exist.
     An import batch that arrives after the Move collapses its new posts under
     the copies the Move adopted.
5. **Local follows.** Oxy has repointed each local account's follow of the old
   account to the target, which is local, so no new remote Follow is needed.
   Each local account that followed the old actor sends it an `Undo(Follow)`
   through the normal unfollow path, and its `federated_follows` row is
   removed. Usernames are resolved in one batched Oxy call. A user Oxy does not
   return keeps the row, and the log counts it (`unfollowUnresolved`).

The Update that lets Mastodon accept the Move is described in
[fediverse](./fediverse.mdx#4-an-account-that-moves-here).

## Guarantees

An imported post is an ordinary published post of the user. It has its own
id, replies, likes and moderation. It differs in these ways:

- **No live side effects.**
  - No notification of any kind: mention, reply, quote or subscriber.
  - No socket broadcast.
  - No push federation delivery.
  - A backfill of years of posts is not news.
- **No mentions.** The people it names were addressed on another platform.
  The post's mention list is always empty, and pasted profile links are not
  turned into mentions.
- **Original date.** `created_at` is the source date, so the post sits in its
  real place on the profile and in chronological feeds.
- **Federation by pull.**
  - The ActivityPub outbox serves public root posts, with `published` set to
    the original date. Remote servers that backfill see them where they belong.
  - An imported content warning federates as `sensitive: true` only, because
    native posts have no `summary` text.
- **Provenance.** The post DTO carries `importedFrom: { platform, sourceUrl }`.
  The app deliberately does NOT render it: an imported post reads as an
  ordinary post of its account (the owner's call, 2026-10-16), and the ledger
  keeps where it came from. An imported content warning becomes
  `metadata.spoilerText` and gates the body the same way a federated one does.
- **Idempotency.** `(oxy_user_id, platform, source_id)` is unique.
  - Resending an item returns `existing` and writes nothing.
  - If two sends of the same item race, the losing one deletes its duplicate
    and also returns `existing`.
- **Classification waits.** The AI classifier leaves imported posts out of its
  main queue. They are classified in batches of 10, only in a cycle that has no
  live posts to process (`PostClassificationService.selectQueue`), so an
  import never delays new posts.
- **Deletion.** The `post_imports` row is removed with its post (`ON DELETE
  CASCADE`) however the post is deleted.

## A Telegram channel export

A channel cannot be imported by Move: a channel is never the subject of a
delegation (`isDelegatedActAsEligibleKind`), and Move imports by acting as the
user. Until that exists, a Telegram Desktop channel export is imported by the
operator-run one-shot `packages/backend/src/scripts/importTelegramChannelExport.ts`
(workflow `.github/workflows/run-telegram-channel-import.yml`):

1. Convert the export into a manifest: one item per post, an album folded into
   one post, dates from `date_unixtime` (the export's `date` is the exporting
   machine's local time).
2. Stage the manifest and its media under `telegram-import/<run>/` of the
   private Cloudflare R2 bucket `mention-import-staging` (Oxy's account
   `fa4392797e57d4e63ceaaf7b1dc687ed`, location WNAM). The bucket deletes every
   object 30 days after upload and aborts incomplete multipart uploads after 10
   days. Mention's task role calls no storage API and holds no storage
   credential, so the task reads only through presigned URLs, and refuses every
   URL that is not exactly
   `https://mention-import-staging.fa4392797e57d4e63ceaaf7b1dc687ed.r2.cloudflarestorage.com/telegram-import/…`:
   virtual-hosted, because a path-style URL's host names every bucket in the
   account. The content never goes to GitHub.

   The operator uploads and presigns with the AWS CLI against R2, using a
   short-lived R2 token scoped to that one bucket (Object Read & Write). The
   token's id is the S3 access key id and the SHA-256 of its value is the secret
   (oxy-infra runbook 61, "Object storage on Cloudflare R2"). Delete the token when
   the import is done.

   ```ini
   # ~/.aws/config
   [profile mention-import-staging]
   region = auto
   endpoint_url = https://fa4392797e57d4e63ceaaf7b1dc687ed.r2.cloudflarestorage.com
   s3 =
     addressing_style = virtual
   ```

   ```bash
   export AWS_PROFILE=mention-import-staging
   aws s3 cp ./media s3://mention-import-staging/telegram-import/<run>/media/ --recursive
   # Presign every media file and write each URL into the manifest, then:
   aws s3 cp manifest.json s3://mention-import-staging/telegram-import/<run>/manifest.json
   aws s3 presign s3://mention-import-staging/telegram-import/<run>/manifest.json --expires-in <seconds>
   ```

   R2 allows at most 7 days (`604800`). A media URL is presigned INSIDE the
   manifest, so its expiry must outlive the whole import, dry run and live run
   included; check the printed URL's host is the virtual-hosted one above.
3. Run the workflow dry, then live. Each media file becomes an asset owned by
   the target account, and every post goes through the same `ingestBatch` as the
   ingest API, so dedupe, undo (`DELETE /imports/v1/batches/<batch>`) and the
   recorded provenance work unchanged.
4. Delete the staging prefix
   (`aws s3 rm s3://mention-import-staging/telegram-import/<run>/ --recursive`)
   and the token. The lifecycle rule deletes anything left behind after 30 days.
